# 배포 가이드 (백엔드)

이 앱은 **단일 인스턴스 전용**입니다. 예약 DB(SQLite)와 업로드 이미지를 로컬
디스크에 두므로 여러 대로 수평 확장할 수 없습니다(오토스케일링을 켜면 인스턴스마다
다른 DB 를 보게 됩니다). 확장이 필요해지면 Postgres + 오브젝트 스토리지로 옮겨야
합니다. 반대로 말하면 **NAS·VPS 한 대에 올리는 구성에는 아주 잘 맞습니다.**

---

## 1. 서버 실행

**운영은 반드시 gunicorn 으로 띄웁니다.**

```bash
pip install -r requirements.txt
gunicorn -c gunicorn.conf.py wsgi:app
```

`python app.py` 는 **개발 전용**입니다. Werkzeug 개발 서버 + 디버거로 뜨기 때문에
운영에 노출되면 디버거를 통해 임의 코드 실행이 가능합니다. 운영용 설정
(`FORCE_HTTPS`, `SESSION_COOKIE_SECURE`, `TRUSTED_PROXY_HOPS`, `HSTS_MAX_AGE`)이
켜진 상태로 `python app.py` 를 실행하면 앱이 안내 메시지를 내고 종료합니다.

워커 수는 `gunicorn.conf.py` 참고 — SQLite 라 쓰기는 어차피 직렬화되므로
프로세스는 적게(2), 스레드를 넉넉히(4) 두는 구성입니다.

systemd 유닛 예시:

```ini
[Unit]
Description=Nareum 대관 예약 API
After=network.target

[Service]
WorkingDirectory=/srv/nareum/BackEnd
ExecStart=/srv/nareum/BackEnd/.venv/bin/gunicorn -c gunicorn.conf.py wsgi:app
Restart=always
User=nareum

[Install]
WantedBy=multi-user.target
```

## 2. 데이터 저장 위치와 백업

`db/*.sqlite3` 와 `static/<slug>/` 는 **로컬 파일**이며 `.gitignore` 에 있습니다.
기본값은 앱 디렉터리 안입니다.

```python
DB_FOLDER   = os.environ.get("DB_FOLDER")   or os.path.join(BASE_DIR, "db")
STATIC_ROOT = os.environ.get("STATIC_ROOT") or os.path.join(BASE_DIR, "static")
```

### 시놀로지 NAS · VPS — 기본값 그대로 쓰면 됩니다 ✅

프로젝트 폴더 자체가 NAS 볼륨(예: `/volume1/web/nareum/BackEnd`) 위에 있으므로
`db/` 도 함께 영구 보존됩니다. **환경변수를 지정할 필요가 없고**, File Station 이나
SMB 로 `BackEnd/db` 폴더를 그대로 열람·다운로드할 수 있습니다.

### 컨테이너(Docker/Container Manager) — 마운트가 필요합니다 ⚠️

이미지 안의 앱 디렉터리에 데이터를 두면 **재배포마다 전부 사라집니다.**
`db/` 와 `static/` 을 NAS 경로로 바인드 마운트해야 합니다.

저장소의 `Dockerfile` 과 `docker-compose.yml` 이 이 구성을 그대로 담고 있습니다.
시놀로지 Container Manager > 프로젝트 에서 이 `BackEnd` 폴더를 지정하면 됩니다.

1. `.env.example` 을 복사해 `.env` 를 만들고 `BackEnd/` 에 올립니다.
   (`.gitignore` 에 있어 저장소에는 없습니다. 비밀번호가 들어가므로 커밋 금지.)
2. `docker-compose.yml` 의 `volumes` 왼쪽 경로 3개를 NAS 실제 경로로 바꿉니다.
3. 프로젝트를 빌드·실행한 뒤 로그에서 초기 비밀번호와 `[storage]` 경로를 확인합니다.
4. DSM 역방향 프록시를 `localhost:8000` 으로 연결합니다.

```yaml
volumes:
  - /volume1/docker/nareum-data/db:/app/db        # 예약 DB
  - /volume1/docker/nareum-data/static:/app/static  # 업로드 이미지
  - /volume1/docker/nareum-data/backups:/backups    # 백업 스냅샷
```

compose 가 `STORAGE_PERSISTENT=true` 를 넣어 주므로 부팅 경고는 자동으로 꺼집니다.

> `/app/static` 을 마운트하면 이미지 안의 기본 시설 사진(`static/img/`)이 가려집니다.
> `docker-entrypoint.sh` 가 첫 실행 때 마운트된 폴더에 원본을 한 번 복사해 넣습니다.

> Cloud Run / Vercel / Heroku 처럼 디스크가 휘발되고 볼륨을 붙일 수 없는 곳은
> 이 앱에 부적합합니다.

부팅 로그에 실제 경로가 찍히므로 배포 후 한 번 확인하세요:

```
[storage] DB_FOLDER   = /volume1/web/nareum/BackEnd/db
[storage] STATIC_ROOT = /volume1/web/nareum/BackEnd/static
```

경고는 "컨테이너 안 + 앱 디렉터리" 조합일 때만 나옵니다. NAS·VPS 직접 실행에서는
경로만 출력되고 경고는 없습니다.

### ⚠️ 가동 중에 `.sqlite3` 파일을 그대로 복사하지 마세요

이 앱은 SQLite 를 **WAL 모드**로 씁니다(여러 워커가 동시에 읽고 쓰기 위해 필요).
WAL 모드에서는 최근 트랜잭션이 본 파일이 아니라 옆의 `-wal` 파일에 먼저 쌓입니다.

```
nareum.sqlite3        ← 이것만 받으면 최근 예약이 빠져 있을 수 있음
nareum.sqlite3-wal    ← 아직 본 파일에 반영되지 않은 변경분
nareum.sqlite3-shm    ← 공유 메모리 인덱스
```

`-wal`/`-shm` 은 **요청이 몰리는 동안에만** 생기고 한가해지면 자동으로 본 파일에
합쳐지며 사라집니다. 그래서 File Station 으로 받아도 대부분은 멀쩡하지만,
하필 예약이 들어오는 순간에 받으면 **그 예약이 없는 파일을 받게 됩니다.**
백업인 줄 알았던 파일에 데이터가 빠져 있는 게 제일 곤란한 경우입니다.

안전하게 받는 방법은 둘 중 하나입니다.

**(권장) 백업 스냅샷을 받으세요.** SQLite 온라인 백업 API 를 쓰므로 가동 중에
실행해도 항상 일관된 단일 파일이 나옵니다.

```bash
python scripts/backup.py
# → BackEnd/backups/2026-08-19_040000/nareum.sqlite3  (그대로 다운로드 가능)
#                                    /super.sqlite3
#                                    /uploads.tar.gz  (업로드 이미지)
```

기본 출력 위치가 `BackEnd/backups/` 라 File Station 에서 바로 열람됩니다.
**File Station 열람 지점을 `db/` 대신 `backups/` 로 잡으세요.**

**(대안) 세 파일을 함께 받으세요.** `-wal`·`-shm` 까지 같이 받으면 복원 시
정상적으로 합쳐집니다. 하나만 받으면 안 됩니다.

### 백업 자동화

```bash
python scripts/backup.py                                        # 기본 위치
BACKUP_DIR=/volume1/backup/nareum BACKUP_KEEP=30 python scripts/backup.py
```

기본 14개를 보관하고 오래된 스냅샷은 자동 삭제합니다.

시놀로지에서는 **DSM → 제어판 → 작업 스케줄러 → 예약된 작업 → 사용자 정의
스크립트** 로 등록하는 게 가장 간단합니다.

```bash
cd /volume1/web/nareum/BackEnd && /volume1/web/nareum/BackEnd/.venv/bin/python scripts/backup.py
```

일반 리눅스라면 크론:

```
0 4 * * * cd /srv/nareum/BackEnd && .venv/bin/python scripts/backup.py >> /var/log/nareum-backup.log 2>&1
```

NAS 디스크가 통째로 고장나는 경우까지 대비하려면 `backups/` 를 Hyper Backup 이나
Cloud Sync 로 외부(R2/S3/다른 NAS)에 한 벌 더 보내두세요.

## 3. 환경 설정

`.env.example` 을 `.env` 로 복사하면 `config.py` 가 임포트 시 자동으로 읽습니다.
셸/systemd 환경변수가 있으면 그쪽이 우선입니다.

HTTPS 프록시(nginx / Cloudflare) 뒤에 두는 운영 프리셋:

```
SESSION_COOKIE_SECURE=true
FORCE_HTTPS=true
TRUSTED_PROXY_HOPS=1
HSTS_MAX_AGE=31536000
DEFAULT_PLACE_PASSWORD=<초기 기관 관리자 비밀번호>
```

> `TRUSTED_PROXY_HOPS=1` 은 두 가지 이유로 필수입니다. ① 프록시 뒤에서
> `request.is_secure` 가 올바로 판정되어 Secure 쿠키가 동작하고, ② 로그인 시도
> 제한이 실제 클라이언트 IP 로 집계됩니다. 0 이면 **모든 요청이 프록시 IP 하나로
> 묶여 이용자 전체가 함께 잠깁니다.**

프론트를 Cloudflare Pages 프록시(`FrontEnd/public/_worker.js`)로 붙이는 구성이면
API 가 same-origin 이 되므로 `CORS_ORIGINS` 는 관여하지 않고
`SESSION_COOKIE_SAMESITE=Lax` 로 충분합니다.

## 4. 초기 비밀번호

- **슈퍼 관리자**: 첫 부팅 시 콘솔에 1회 출력 → 로그인 후 즉시 변경.
  (`SUPER_PASSWORD` 로 지정 가능)
- **기관 관리자**: `DEFAULT_PLACE_PASSWORD` 미지정 시 **`manage123`** 이 됩니다.
  공개 URL 에 붙는 순간 위험하므로 반드시 지정하거나 즉시 변경하세요.

로그인은 IP 별로 `LOGIN_MAX_ATTEMPTS`(기본 10)회 실패 시
`LOGIN_LOCKOUT_SECONDS`(기본 15분) 동안 잠깁니다.

## 5. 배포 후 점검

```bash
curl https://<도메인>/api/health            # {"status":"ok", ...}
```

- [ ] 부팅 로그의 `[storage]` 경로가 실제 보존되는 위치를 가리키는가
- [ ] `[storage] ⚠️` 경고가 없는가 (컨테이너면 바인드 마운트 확인)
- [ ] 기관 관리자 비밀번호가 `manage123` 이 아닌가
- [ ] 슈퍼 비밀번호를 변경했는가
- [ ] HTTP 로 접속 시 HTTPS 로 리다이렉트되는가
- [ ] 로그인 10회 실패 후 429 가 나오는가
- [ ] `scripts/backup.py` 가 작업 스케줄러/크론에 등록되어 있는가
- [ ] 백업 스냅샷이 한 번 이상 실제로 생성됐는가
- [ ] `/api/health` 를 외부 모니터(UptimeRobot 등)에 등록했는가
